## 2. Recommended model and scope

Prefer `meta-llama/Llama-3.1-8B-Instruct` if the PI has or can promptly obtain
official access. It gives a cross-family test and is closer to the existing
incremental chat implementation than Mistral. The official model is gated and
requires acceptance of its license and contact-information sharing; access has
not been verified. Pin a full model revision and tokenizer manifest before any
pilot. Both sides use separate states of the same new model; do not connect a
Qwen instance to a Llama instance or train weights/interfaces.

`mistralai/Mistral-7B-Instruct-v0.3` is an openly downloadable alternative, subject
to PI choice before outcome inspection. Its native template moves system text
into the last user turn and requires alternating roles. This conflicts with
prefix-stable saved caches and the current consecutive-user LANG path. A fixed
first-user system preamble and merged user segments would need an explicit,
tested serialization policy. Its official config has `sliding_window: null`;
sliding-window attention is not an inherent blocker for this checkpoint.

Recommend starting with these five conditions, using the existing semantic task
and outcome definitions:

| Condition | Purpose |
|---|---|
| C0 | Own/partner task and format baseline |
| One-way fixed partner memory, FULL | Replicate the central attribution effect |
| Same memory and weight, RF | Cut the link only at readout, from the same saved reflection state |
| Content-counterfactual KV | Change only donor rule/code-word content and measure access to that change |
| Strict-third-person donor memory | Test attribution with explicitly named third-person source content |

This is a core replication. It would not establish that the matched steering
comparison, tagged/untagged text comparison, open-report coding or reciprocal
live-loop results all generalize. Those remain Qwen-specific unless separately
replicated. A full matched-route replication requires new calibration and more
conditions; do not reuse Qwen's layer-24 calibration or steering gain.

## 3. What the new protocol must settle before execution

Write and review a separate `PROTOCOL_V4.md`, then freeze it and its configs before
formal data collection. The following is the proposed basis, not an executable
specification:

- New, disjoint baseline, strength-pilot, signal/variance-pilot and formal splits.
  Keep the original semantic materials and episode as the statistical unit;
  tokenization and all balanced option orders must be revalidated for the new model.
- A 60-episode baseline check; a 40-episode fixed-memory strength pilot over the
  existing `w = {0.3, 0.5, 1, 2, 3}` grid. Select only from ACC, CAP and format,
  never attribution, self-reports or significance. Specify exact eligibility,
  strength and tie-breaking rules in v4 before running. Any use of the v2
  thresholds must be explicit, and logit effect magnitudes must not be treated as
  calibrated across models.
- Preserve the existing separate signal/variance-pilot and PI checkpoint unless
  the PI explicitly approves a different design. The inherited rule uses 80 new
  episodes, then chooses 300-600 formal episodes from paired variance after
  parameter selection is frozen. Budget for the 600-episode ceiling, rather than
  quietly shrinking N near the deadline. Specify which comparisons determine N.
- Prespecify the primary attribution contrasts, the content-access validity
  check, multiplicity correction and episode-level intervals. Keep M, M_NOW,
  M_WORD, ACC, CAP and format definitions, reporting the self/partner components.
- Check pronoun cleanliness, partner access and attention for the third-person
  condition. Without strength matching and a prespecified equivalence test, do
  not describe it as retaining a chosen percentage of the original effect.
- Report failures, missing trials and null results. A failed gate is not a reason
  to search for a more favorable model, prompt or weight. Do not pool episodes
  from the two models as independent evidence of broad model-family generality.

## 4. Engineering acceptance checks

The current implementation hardcodes Qwen in `runtime.py`, `chat.py`,
`conditions.py`, `run.py` and the GPU setup script. Add an explicit model profile
and propagate model/revision, architecture, tokenizer hash and serialization
version through calibration, condition and resume identities. Preserve existing
Qwen defaults and regression tests.

The bridge attention math is dimension-driven and potentially reusable. Static
inspection of Transformers 4.57.1's Llama/Mistral interfaces is encouraging, but
does not establish GPU correctness. Before interpreting any new-model result:

1. Verify incremental serialization against the frozen profile's reference
   serializer. For an unmodified native template, also require exact agreement
   with `apply_chat_template`; document any approved departures from that
   template. Existing tokens must remain unchanged when appending a turn. Verify
   all stop tokens, answer-label tokens at their actual positions and prefix lengths.
2. Verify unbridged/zero-weight equivalence, mask and padding behavior, donor
   causality, position handling and invocation at every decoder layer.
3. Verify independent snapshots/readout branches and FULL/RF branching from the
   same state. Preserve the prespecified reflection and report token limits.
4. Verify donor counterfactuals do not change receiver input and that labels have
   usable probability mass. Run task suitability gates before strength selection.
5. Start with 1-2 smoke episodes and conservative batches; measure peak memory
   and throughput, including readout branching and FP32 output-head overhead.

All local work is offline and torch-free. Model execution belongs on the rented
GPU, in a new directory such as `/workspace/mind-connecting-v4`. Existing frozen
remote directories, tokenizer files, calibration and results remain untouched.
